# LEVRA — Campaign Decision Engine

## 1. Что строим

LEVRA — агент планирования тарифных кампаний, который проверяет гипотезы пилотами,
распределяет ограниченный бюджет и делает каждое решение проверяемым для маркетолога.
Рабочее имя проекта; проверка товарного знака/домена не проводилась.

**Наш дополнительный вклад:** не ещё один список кампаний, а цикл
**исследование → план → проверка → изменение условий → пересчитанный план с доказательствами**.

Пользователь — аналитик маркетинга. Три отличия сверх базового ТЗ:
1. What-if-пересчёт из одного снимка знаний без повторной траты пилотного бюджета.
2. Паспорт кампании: данные, пилоты, неопределённость, альтернативы, причины выбора/отказа.
3. Проверка целого плана: бюджет, порядок, пересечения и зависимость от слабых наблюдений,
   с возможностью исправить план, а не только вывести предупреждение.

Не делать полноценную CRM, реальную рассылку, биллинг, авторизацию, очереди микросервисов,
векторную базу и отдельную модель для каждого клиента. В продукте используется синтетическая среда,
а не фактическая интеграция с Beeline. Не называть net_arpu_gain реальной прибылью или causal uplift.

## 2. Приоритет и архитектура

Сначала сильное запускаемое ядро. Интерфейс строится вокруг этого же ядра, а не вокруг демо-JSON.

Предлагаемый состав:
- `agent.py`: self-contained entry point и численные helpers; не импортирует UI, сервер или mock truth.
- `tools/`: read-only аудит, бенчмарки, генерация трассировки и проверка исходников.
- `tests/`: unit, integration, воспроизводимость и собственные синтетические stress-сценарии.
- `backend/`: тонкий API для запуска агента, хранения run artifacts и what-if replan.
- `frontend/`: React + TypeScript, компактное рабочее место аналитика; сборка локально,
  без CDN в демонстрации. FastAPI — допустимый тонкий Python backend.
- `reports/`: проверяемые результаты реальных запусков, явно разделённые по источнику.

Если текущий репозиторий уже содержит подходящий стек, использовать его вместо переписывания.
Не вводить Node-зависимости в официальный Python scoring path. Точные версии зависимостей
фиксировать после установки и фактической проверки. Никакого обязательного GPU.
Предпочтительно сохранять scoring core команды в одном agent.py: формат сдачи перечисляет этот файл,
а отдельная доставка внутренних Python-пакетов явно не описана. UI может импортировать наши классы
из agent.py. В командах запуска использовать корень официального репозитория.

## 3. Контракт среды: прочитать до реализации

Agent.act получает customer_profile, tariffs, channels, остатки ресурсов и run_pilot.
Входные объекты env считать read-only, кроме разрешённых вызовов env.run_pilot.

Лимиты: финальных кампаний 1–10; максимум 5 000 контактов на кампанию;
15 000 контактов и 100 000 у.е. суммарно вместе с пилотами;
20 пилотов максимум; запрашиваемый размер 10–200, фактический n_actual может быть меньше.

Разрешённые фильтры:
- filter_arpu_segment: LOW/MID/HIGH;
- filter_data_segment: NON_USER/LITE/HEAVY;
- filter_call_segment: LOW/MEDIUM/HIGH;
- filter_current_tariff: код или несколько кодов через `;`.

Пропуск фильтра означает отсутствие ограничения. Не добавлять фильтры по ID, прогнозному ARPU,
произвольному диапазону чисел, исключённым ID или размеру финальной кампании: контракт их не задаёт.
explicit_ids предназначен только для внутренних записей пилотов, не для финального вывода агента.
Не предлагать клиенту его же тариф как способ манипулировать результатом.

Порядок важен: аудитория по фильтрам → сортировка ID → 5 000 → остаток контактов → остаток денег.
Вычесть ВСЕ коммуникационные расходы, включая повторные. Для каждого контактированного клиента
взять максимум эффектов среди его кампаний, даже если этот максимум отрицательный. Для человека,
которого не контактировали, эффект ноль. Не обрезать отрицательные эффекты до нуля.
Санитайзер может отбросить неверную кампанию, но мы должны валидировать её ДО возврата.

## 4. Работа с данными

Сначала `docs/DATA_AUDIT.md`. Объёмы и тарифы читать из файлов/объектов, не зашивать константы.
Не соединять целевую базу с историей по ID: пересечений нет. predicted_arpu уже предоставлен —
использовать его в оценке денежного эффекта, не переобучать его и не заменять в env.

История даёт слабое prior для (current_tariff, arpu_segment, target_tariff):
- устойчивое before/after относительное изменение с явным контролем малых знаменателей;
- число наблюдений и pooling к более широким группам при малом числе примеров;
- стоимость/пакеты исходного и целевого тарифа как контекст, не номер tariff_N;
- долю направления в истории можно использовать только как heuristic adoption prior;
  нет данных о всех офферах/отказах, значит это НЕ измеренная conversion кампании.

Необходим ненулевой floor неопределённости из-за сдвига аудитории: большая историческая выборка
не должна делать prior непоколебимым. Этот floor — гиперпараметр, который тестируется на собственных
сценариях сдвига; не выдавать его за число, предоставленное организатором.
Сохранять отрицательные гипотезы и непривлекательные сегменты в evidence как отклонённые,
не форсировать upsell по цене и не объявлять HIGH автоматически лучшим.

traffic/arpu_monthly — источник диагностики и, при наличии времени, исторических агрегатов.
Не обучать тяжёлую end-to-end модель до работающего агента. Учитывать дубли/кратность join,
документировать выбранную обработку только в собственной копии; оригиналы неизменны.

## 5. Агент: выбираем эксперименты ради будущего плана

### Первый работающий алгоритм

A. Составить валидные базовые клетки current_tariff × arpu_segment и их размер/сумму predicted_arpu.
   Пропуски хранить в диагностике, не придумывать значения. Модель эффекта публичного scorer имеет
   именно эти клетки плюс target/channel. data/call-фильтры меняют состав и масштаб аудитории;
   не утверждать, что они сами добавляют индивидуальный causal response в данной модели.
B. Создать кандидаты переходов из истории и допустимого справочника. У неподтверждённых направлений
   сохранять широкую неопределённость и поддержку разумного исследования. Не ограничивать всё
   зашитыми tariff_8/tariff_9 или только известными "победителями" мока.
C. Провести первые полезные пилоты, учитывая масштаб возможной финальной кампании и расход ресурсов.
D. Обновить оценки по observed_lift_ratio и n_customers, а не по впечатлению от знака одного пилота.
E. Построить предварительный план. Выбирать следующий пилот там, где уменьшение неопределённости
   способно поменять выбор кампании/канала или распределение значительной части ресурсов.
F. Остановить исследование, когда дополнительная информация не оправдывает стоимость и потерю
   оставшегося охвата, либо достигнут time/resource budget. Не обязательно расходовать все 20.
G. Сформировать 1–10 валидных финальных кампаний, проверить их порядок и лимиты.

Начать с простой проверяемой эвристики этого цикла и улучшать по тестам; не обещать точное
глобально-оптимальное решение или точный value of information, пока это не реализовано и не доказано.

### Статистика пилотов

В environment.py шум y имеет std = 0.804/sqrt(n_actual). Для одной однородной клетки это позволяет
реализовать Normal–Normal обновление среднего и дисперсии либо иную прозрачную оценку.
Использовать фактическое n_actual, не запрошенное. Повторные пилоты взвешивать по точности.
При смешанных клетках учитывать дополнительную неоднородность; самый простой первый вариант —
пилотировать однородные клетки, объединять их в финальном плане только после оценки.

Множитель канала применяется к conversion и ограничен сверху 1.0. Поэтому нельзя безусловно
масштабировать оценку между каналами. Для каналов с multiplier <= 1 линейный перенос предполагает
валидную conversion в [0,1]; явно записать это предположение. У call multiplier=1.20 есть насыщение.
Не переносить SMS→call линейно без модели насыщения, консервативных границ или отдельного пилота.
Можно начать с отдельно учитываемых channel-specific оценок, чтобы избежать ложной точности.

Решение о размере пилота учитывать совместно с каналом: push экономит деньги, но не контакты;
SMS/ads дают другую силу сигнала за другие расходы. Звонки не запрещать априори, но проверять
их предельную ценность. Все экономические показатели получать кодом, не от LLM.

### Память разрешённых действий

Создать собственный журнал на каждый вызов run_pilot:
filters, target, channel, requested_n, actual_n, cost, observed_ratio,
prior/posterior snapshots, ресурсы до/после, краткая причина выбора следующей проверки.
В public pilot_history отсутствуют фильтры и sampled IDs. Не пытаться их добыть из internals.
Журнал содержит краткие проверяемые обоснования действий, не скрытые рассуждения модели.

## 6. Оптимизация плана

Нужна оптимизация СОВОКУПНОГО net, а не сортировка среднего ratio.

Для каждой валидной кампании оценить реальную аудиторию после разрешённых фильтров и ограничения
5 000, денежную ценность predicted_arpu × estimated_ratio, стоимость контактов и неопределённость.
Разбивать большие сегменты только доступными фильтрами; точный размер кампании задавать нельзя.

Первый solver: детерминированный greedy по предельному вкладу с учётом денег/охвата/слотов,
затем локальные замены/перестановки. Улучшить до beam search либо другого ограниченного поиска,
если он показывает измеримый выигрыш и укладывается во время. Не выбирать метод по модному названию.

Предпочитать непересекающиеся финальные аудитории, если overlap не даёт обоснованного прироста.
Не начислять повторный полный эффект за ту же аудиторию и не заставлять solver тратить весь бюджет.
Точно считать пересечения финальных фильтров и окончательное усечение по порядку.

Пилотные контакты известны по количеству, расходам и фильтрам, но их ID скрыты. Это даёт точный
resource ledger, но не точное клиентское пересечение. Оценивать pilot overlap вероятностно по
публичной схеме случайной выборки либо консервативно; раскрывать приближение. Не помечать эту часть
как exact. Сложную симуляцию включать только если она успевает, с собственным фиксированным RNG.

Снимок знаний и итоговый plan manifest сохранить после act для демо. Ошибка записи отчёта не должна
ломать возвращение плана. При новом act очистить состояние и не читать результаты предыдущих seed.

## 7. Наши дополнительные продуктовые функции

### What-if replan — главное отличие

После завершения исследования пользователь меняет общий бюджет, доступные каналы,
максимальное число финальных кампаний. Получает пересчитанный план из того же снимка знаний.
Показывать сравнение плана до/после, изменения ожидаемого net/охвата/расхода и причины.

Новые пилоты при таком действии НЕ запускаются. Потраченные деньги/контакты не возвращаются.
Новый общий бюджет ниже уже потраченного — недопустимый сценарий, а не отрицательный остаток.
Изменённые ограничения НЕ передаются как патч в официальный scoring_core:
официальная оценка остаётся на исходных правилах; what-if — отдельный прогнозный расчёт.
Сценарные прогнозы нельзя подписывать как фактические результаты скрытого судейства.

### Decision passport

В карточке: аудитория, тариф/канал, ожидаемый net, неопределённость, источники prior, проведённые
пилоты, дата/ID снимка, лучшая отвергнутая альтернатива и конкретная причина.
Все числа берутся из моделей/журнала. Возможны статусы: историческая гипотеза, проверено пилотом,
неопределённо, отклонено. Не выдавать произвольный confidence score за калиброванную вероятность.
Показывать какие новые сведения способны изменить рекомендацию без обещания точного будущего.

### Plan audit and repair

Отдельные проверяемые правила обнаруживают некорректные фильтры, расход сверх допустимого,
пересечения, опасное усечение последней кампании и концентрацию на слабо проверенной гипотезе.
Для исправления использовать тот же solver/валидатор. Показать before/after и проверку результата.
Не заменять это двумя LLM, которые просто соглашаются друг с другом.
Измерить вклад проверки через сравнение с выключенным компонентом на фиксированных тестах.

## 8. Интерфейс и демо

Компактный аналитический продукт, не чат на весь экран и не лендинг.
Основной экран: запуск исследования, шаги/пилоты, 4–5 ключевых показателей и план кампаний.
Вторая область: сравнение условий, изменившиеся кампании и их паспорта.
Третья: сравнение реальных запусков, статус проверок, предупреждения о данных.

Каждый run виден как `Official mock`, `Custom synthetic stress` или `Forecast/what-if`.
Статус live execution отличается от replay сохранённого запуска. Не воспроизводить лог как
якобы свежий запуск. Не показывать случайные цифры или захардкоженные победы.
При неизвестном показателе показать "нет оценки", а не выдуманное число. Без стоимости контактов
ROI математически не определён для сравнения как конечный множитель — отдельная подпись.

API предлагается минимальный: создать run, получить status/trace/plan, выполнить replan,
получить evidence кампании. Артефакты сохранять в файловом хранилище run_id, без обязательной БД.
Локальное приложение должно запускаться одной понятной командой после установки зависимостей.
Никаких реальных отправок клиентам. Кнопку назвать "Исследовать в симуляции", не "Запустить Beeline".

## 9. LLM: содержательно, но не критическая зависимость

Численное ядро работает без интернета. Сама модель Astra в Codex — инструмент разработки,
не обязательный runtime-компонент агента. Не придумывать API-ID модели из её названия в интерфейсе.

Если остаётся время: LLM переводит человеческий запрос аналитика в валидированные ограничения
и предлагает действия только из зарегистрированных инструментов/кандидатов. Например,
"сократи бюджет, исключи звонки" → typed constraints → показ пользователю → apply → replan.
Это реальная функция продукта, но не замена learning/pilot loop и не косметический текст.

Отдельный opt-in LLM-assisted research режим допустим только с явно установленным флагом,
фиксированными timeout/call budget и fallback. Не включать автоматически по OPENAI_API_KEY.
В scoring/submission по умолчанию один детерминированный offline путь. Никаких записанных ответов,
выдаваемых за свежий вывод модели. При отсутствии API модель отключена, ручные формы работают.
Ключ только в окружении; не логировать его и не отправлять весь customer_profile наружу.

## 10. Тесты и доказательства

Проверить как минимум:
- интерфейс act, 1–10 кампаний, существующие тарифы и все допустимые фильтры;
- вызов пилотов и изменение решений при изменённых наблюдениях, не только их присутствие в логах;
- n_actual, малые/пустые группы, пропуски, ограниченный остаток и отрицательные результаты;
- бюджеты пилотов + финала, усечение 5 000, порядок, повторные контакты, channel saturation;
- отрицательный best effect не превращается в 0;
- evaluator не требует модификаций, env inputs не мутируются;
- what-if не вызывает новые пилоты и учитывает sunk costs;
- новая копия Agent не наследует posterior/evidence от предыдущего запуска;
- default offline работает при наличии и отсутствии API key одинаково;
- свежие процессы дважды создают байтово одинаковый submission.csv;
- отсутствие подглядывания/зависимостей на mock impact и synthetic oracle в agent.py;
- UI/API smoke test реального запуска и replan, README clean-start test.

Сравнивать на совпадающем наборе seed: исходный template, history-only,
fixed pilots, adaptive LEVRA и при возможности ablations отдельных компонентов.
Повторение с разными seed на одном mock проверяет ШУМ, но не сдвиг модели эффектов.
Поэтому дополнительно сделать отдельные synthetic stress-сценарии:
prior overestimation, знак некоторых эффектов меняется, новый ранее редкий полезный переход,
общая слабая результативность, неприятные первые пилоты, ограниченные ресурсы, насыщение call.
Это тесты нашей конструкции, не угаданный hidden model. Доступ к true effects есть только у
тестового harness; агент получает лишь env и пилоты. Не импортировать fixture truth из агента.

В бенчмарках: mean/median/min net, positive-runs, runtime, cost, contacts, unique coverage,
число пилотов, seed/mode/source. Предельные исходы показывать, а не скрывать ради красивого среднего.
Издержки LLM не входят в официальный objective; если измеряем, показывать отдельной строкой.
Не объявлять победу по мок-скорингу, не называть сравнение с template достаточным доказательством.

## 11. Этапы реализации

Этап 1: baseline, работающий adaptive core, basic tests, official evaluation, generated submission.
Этап 2: более сильный resource-aware solver, audit trace, сравнения и determinism.
Этап 3: UI, evidence passports, what-if без новых пилотов, plan repair.
Этап 4: stress tests, smoke test UI, README, optional LLM при наличии времени, чистая сдача.

Не ждать идеального дизайна или уточнения спорного LLM-режима, чтобы сделать этап 1.
При обнаружении реального блокера сохранить работающее ядро и явно описать блокер.
Финальный отчёт Codex: что сделано, какие команды реально запускались, результаты, ограничения,
оставшиеся риски и точная команда запуска для команды. Не заканчивать только архитектурным планом.
