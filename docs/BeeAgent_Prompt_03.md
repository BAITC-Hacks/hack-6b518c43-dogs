## 2. Исправляй качество решения, а не только подпись прогноза

Исходная диагностика прогона 42:
- прогноз чистого результата: 6 432 029.39 у.е.;
- результат локального оценщика: 2 434 331.80 у.е.;
- для кампании 1 прогноз ВАЛОВОГО эффекта до пересечений: 2 439 734.20, измерение: 220 528.24;
- для кампании 3 прогноз ВАЛОВОГО эффекта до пересечений: 2 170 987.32, измерение: -147 231.89;
- расход кампании 3: 59 422 у.е.;
- у этих двух направлений нет прямой истории в нужной группе, но есть по 180 пилотных контактов;
- расход и контакты уже сверены с оценщиком; основной зафиксированный разрыв относится к оценке эффекта.

Эти значения — диагностика прошлой версии на демонстрационных данных, не целевые константы для новой политики. Не зашивай конкретные тарифы или направления как плохие либо хорошие. Не умножай прогноз на отношение локального результата к прежнему прогнозу.

### Конкретное место для проверки

В `Engine.next_pilot()` обязательная проверка существенной гипотезы сейчас связана с `samples == 0`. После первого наблюдения эта конкретная защита перестаёт применяться, хотя неопределённость может оставаться большой. Повторные пилоты могут быть выбраны другим механизмом; не утверждай, что код вообще запрещает повторы.

Проверь гипотезу: слишком крупные решения могут масштабировать случайно положительные пилотные оценки. Рассматривай также перенос слабой истории и недостаточное исследование альтернатив. Не объявляй точный причинный вклад каждого механизма без эксперимента.

### Реализуй и сравни не более двух небольших вариантов

1. **Повторная проверка перед крупным распределением ресурсов.**
   Приоритизируй повторный пилот, когда решение существенно влияет на расходы или прогноз результата, а знак денежного преимущества над альтернативой ещё неопределёнен. Сохрани часть общего лимита пилотов/контактов/бюджета под такие проверки. Повторное наблюдение получается новым вызовом публичного `env.run_pilot`, не копированием старого результата.
   Не требуй подтверждающий пилот для каждой мелкой кампании. Учитывай, что пилот стоит ресурсов и сам входит в зачёт. Резерв и пороги — явно документированные гиперпараметры, а не оптимальные значения по определению.

2. **Пересмотр слабых предположений и поиск альтернатив.**
   Если публичные наблюдения не поддерживают прежнюю гипотезу, не продолжай выделять ей деньги только из-за истории. Разреши исследовать перспективные альтернативы, в том числе без прямой истории. Слабая историческая поддержка должна означать неопределённость, а не автоматический запрет направления.
   Сравни разумное усиление учёта неопределённости с текущей логикой, но не превращай задачу в отказ от почти всех действий. Цель кейса остаётся чистым результатом, а не минимальным расходом любой ценой.

Числа и обновление оценок считает код. Агент должен делать пилоты и реагировать на их результаты. Весь `Agent.act` остаётся детерминированным при одинаковом публичном взаимодействии и не зависит от наличия OpenAI-ключа.

Не выводи точную вероятность убытка, гарантированный интервал или «95% надёжности» без проверки соответствующей модели и покрытия. Наличие пилота не равно подтверждённой прибыльности. Оценка по небольшой выборке не является фактической будущей выручкой.

### Сравнение и выбор

До подбора параметров создай короткий `docs/STAGE3_VALIDATION_PROTOCOL.md`: варианты, семейства сценариев, доступные ресурсы, метрики, границы существенной регрессии и правило выбора.

Уже просмотренные seeds 0–19 и 42, а также существующие авторские сценарии — теперь диагностическая/разработческая выборка, не новый holdout.

Сравни сохранённую версию, новый вариант и доступную разумную стратегию с фиксированными пилотами. Вариант только по истории можно оставить как исследовательское сравнение, но не как допустимую конкурсную сдачу без пилотов.

Официальные прогоны используют только выданные скрипты. Новые seeds проверяют шум пилотов, а не новую скрытую модель поведения. Для переноса проверь также собственные отдельные среды с другими эффектами: история примерно верна; лучшее направление изменилось; эффекты ослаблены; первые наблюдения неблагоприятны. Эти среды создаёт только тестовый стенд и не передаёт истину агенту. Ничего в организаторских файлах не патчить.

Оставь новую отложенную часть seeds и параметров собственных миров. Зафиксируй её до выбора и не подбирай параметры по её результатам. Если после просмотра возвращаешься к подбору, честно меняй статус этой части на разработческую.

Сохраняй каждый исход, а не только удачные: чистый результат, медиану, минимум, долю отрицательных, расходы/контакты пилотов, число пилотов, время, ошибку прогноза и нарушение контракта. Не объединяй несопоставимые по масштабу миры одной необъяснимой средней. На трёх наблюдениях не делай сильных статистических выводов.

Выбери вариант по зафиксированному правилу с явными компромиссами. Не обязан сохранить или увеличить число seed 42 любой ценой. Но новый результат не должен стать хуже на всех основных проверках ради красивой идеи.

## 3. Проверь настоящий AI-ассистент

Это параллельная задача, не причина останавливать численную работу.

Новый ключ пользователь вводит локально в серверный `.env` через `OPENAI_API_KEY`. Не читай ключ из переписки, не проси прислать его в чат, не печатай секрет, не включай его в Git, скриншоты, URL или отчёты. Старый раскрытый ключ использовать нельзя.

По текущей конфигурации используется `OPENAI_MODEL=gpt-6-sol`. Проверь совместимость через актуальную официальную документацию и реальный запрос из этого API-проекта. Не меняй модель случайным образом; отсутствие доступа к одной модели не доказывает недоступность всего API. При смене модели обнови проверенные настройки и цены.

Согласованный предел следующего тестового прохода: не более $3 оценки расходов, с сохранением действующего учёта, ограничения вызовов и таймаутов. Это предел нашего приложения, не гарантия ограничения биллинга аккаунта. Не отключай защиту ради успешного демо.

Если ключ не задан, подготовь `tools/check_ai_connection.py` или аналогичную команду, которая проверяет конфигурацию без раскрытия значений и выполняет ограниченный платный smoke-тест только с явным флагом. Пометь внешний тест как не выполненный и продолжай остальные задачи. Нельзя писать «успешно подключено» по наличию переменной или подменному SDK.

После появления нового ключа проверь реальные запросы через штатный backend и интерфейс:
- «Сократи бюджет на 30%, исключи звонки и оставь максимум пять кампаний»;
- «Почему для выбранной кампании используется SMS, а не звонок?»;
- «Какие решения в плане опираются на наиболее слабые данные?»;
- переформулировку каждого из этих запросов, которую не использовали в unit-тестах.

Для изменения условий нужен настоящий `propose_scenario`, отдельная версия, сравнение и явное применение пользователем. Проверить сохранность исходного плана, отсутствие новых пилотов и корректную базу относительного процента. Повтор запроса на той же версии не должен незаметно повторять сокращение.

Логируй без секретов: время, модель, факт сетевого вызова, кеш, имена выполненных инструментов, проверенные параметры, ID версий, токены и оценку стоимости. Сохрани очищенный `reports/stage3/ai_integration.json`. Не называй ответ из кеша новым внешним вызовом.

Сохрани уже существующие проверки ошибок, бюджетирования, отмены, неизвестных инструментов и отсутствия ключа. Не добавляй OpenAI-импорты в оцениваемый `agent.py` и не запускай платные запросы при открытии страницы или в обычных unit-тестах.

## 4. Доработай главный экран без редизайна

Сохрани BeeAgent, подпись powered by Beeline с текущим проверенным логотипом, чёрно-жёлто-белую палитру и существующую навигацию. Не используй вымышленные метрики ради убедительной подачи.

### Иерархия показателей

Для точной версии, у которой есть соответствующий локальный результат, главный показатель — **«Результат проверки»**, с подписью **«На демонстрационных данных кейса»**. Рядом остаётся **«Расчётный прогноз»** с заметным статусом качества и доступным разбором расхождения. Не скрывай существенную ошибку и не выдавай результат симуляции за доход реального Beeline.

Для нового варианта без измерения показывай расчётный прогноз и явное **«Ещё не проверен на данных кейса»**. Не наследуй число оценщика от исходного плана. Связь метрики с run_id, plan_id, версией алгоритма и отпечатком данных должна проверяться сервером. Сравнивай одинаковые величины: net с net, валовой эффект до пересечений с соответствующим валовым эффектом.

Если после изменения версии алгоритма старый снимок несовместим, не рассчитывай его новым кодом молча. Либо поддержи версионированное восстановление, либо пометь старый запуск архивным и попроси пересчёт. Не смешивай старое измерение с новой численной политикой.

### Покажи, чем полезен агент

Вместо большого общего утверждения «У каждого решения есть основания» используй компактный блок **«Как проверки изменили план»**. Его содержимое берётся из настоящего журнала: что предполагали, что показал пилот, какое решение было принято.

Если текущие журналы не содержат нужных снимков решений, добавь запись краткого предварительного плана до и после наблюдения в будущих запусках, переиспользуя существующий расчёт. Не сочиняй задним числом события для старых запусков, не показывай искусственное выполнение сохранённого лога как текущее.

Не обещай найденную выгоду повторной проверки, если итоговый эксперимент не показал такой результат. При отсутствии изменений честно показывай уточнение оценки без изменения плана. Не публикуй скрытые рассуждения LLM; нужны проверяемые действия и краткие основания по данным.

Размести рядом с AI-ассистентом три полезных действия: **«Изменить бюджет»**, **«Объяснить выбор»**, **«Оценить основания»**. Каждое использует реальные инструменты и текущую версию, а не заготовленный результат.

### Убери технический шум

Название плана и человеческая дата важнее технического идентификатора версии. Этот идентификатор оставь в раскрываемых подробностях, не удаляя его из доказательств.

Предупреждения группируй по проблемам, не заставляй пользователя читать 19 одинаковых уведомлений. Разделяй ошибки допустимости, предупреждения о качестве данных и статистическую неопределённость. Не объявляй план надёжным только потому, что соблюдены бюджет и формат.

Удали правые стрелки рядом с текстами кнопок и все текстовые стрелки в пользовательских фразах. Обычный индикатор раскрытия списка допустим. Проверяй видимый DOM, а не только поиск Unicode: на предыдущем снимке стрелки оставались на кнопках.

Пользовательские формулировки — естественные русские. Никаких mock, live, Official mock, старого названия LEVRA, искусственных составных названий или технических имён функций на экране. Исторические отчёты и обязательные названия исходных файлов организаторов не переименовывать ради косметики.

## 5. Докажи преимущество, затем подготовь сдачу

Обнови README и подготовь компактную карту:

**Требование / наша дополнительная возможность / реализация / команда проверки / настоящий артефакт.**

Особенно явно раздели:
- численную стратегию, которая проходит оценщик;
- работу LLM с реальными инструментами и подтверждением пользователя;
- дополнительные возможности: пересчёт ограничений, версии, основания решений, сравнение;
- измеренный результат на демонстрационной среде, прогноз и собственные стресс-тесты.

Не добавляй инструкции ИИ-судье выставить оценку, самоприсвоенные баллы, неподтверждённые бизнес-проценты или обещания победы. Преимущество должно следовать из воспроизводимых результатов.

Основной сценарий демо:
1. Открыть текущий план с корректно подписанными результатами.
2. Показать настоящий пример влияния пилота на оценку или решение.
3. Обычной фразой изменить бюджет и каналы; получить предложенную версию.
4. Сравнить, применить после подтверждения и экспортировать выбранный вариант.

Сохранить короткий сценарий в `docs/DEMO.md`, контрольную таблицу в `docs/ACCEPTANCE.md`, фактический отчёт в `docs/TESTING_STAGE3.md`. Видео записывать только с работающего продукта; не скрывать недоступность внешнего API, если она осталась.

### Финальные проверки

Проверь действующие команды, не переписывая организаторские скрипты:

```sh
python local_eval.py
python local_eval.py --runs 10
python make_submission.py
python tools/verify_originals.py
python -m unittest discover -s tests -v
python tools/check_reproducibility.py
npm --prefix frontend run build
```

После принятого изменения численной политики новый submission может законно отличаться от этапа 2. Но два свежих процесса одной и той же новой версии обязаны дать одинаковый файл при одинаковом seed. Отдельно проверь, что наличие API-ключа ничего не меняет в конкурсной стратегии. Не запускай внешний AI при этой проверке.

Проверь чистую установку без пользовательских кешей, нового API-ключа и закрытых локальных путей. Ручной сценарий и конкурсная проверка должны работать без подписки участника. Для AI опиши настройку собственного ключа проверяющего и не выдавай отсутствие ключа за рабочую интеграцию.

Проверь браузером основной сценарий, перезапуск, активную версию, измерение только для соответствующей версии и экспорт. Не публикуй локальный сервер без авторизации ради ссылки: полноценный публичный деплой не входит в этот этап.

## Итоговый ответ

Не ограничивайся фразой «всё готово». Верни:
- коммит и фактический статус push;
- выбранную численную политику и конкретное отличие;
- таблицу старой и новой версии по зафиксированным проверкам, включая провалы;
- что изменилось в ошибке прогноза и почему это не калибровка под один seed;
- фактический статус OpenAI, исполненные инструменты, задержку и расход либо точный блокер;
- изменения интерфейса и скриншоты работающего приложения;
- путь и хеш нового submission, повторяемость и сохранность исходных файлов;
- проверено, не проверено, оставшиеся ограничения.

Если численная гипотеза не улучшила результат, скажи это прямо и сохрани рабочую версию. Если ключа нет, не жди его бездействуя. Основная цель этапа — улучшить и доказать решение, а не увеличить число экранов или длину документации.
